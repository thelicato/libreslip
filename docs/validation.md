# Release candidate validation

Validated on 25 September 2026 for LibreSlip 0.12.0, Android application identifier `io.thelicato.libreslip`.

| Check | Result |
| --- | --- |
| Dart formatting | Passed across application, test and integration-test Dart sources. |
| Static analysis | Passed with no issues. |
| Unit and widget tests | All 85 active tests passed; the normal run skipped only the opt-in render capture. |
| Client certificate pinning | Passed real loopback TLS pairing with the generated self-signed Server identity. The Client uses a trust store with no roots and accepts only an exact SHA-256 certificate pin; a mismatched certificate was rejected. Redirects are disabled and the status identity must report the same fingerprint before the one-time code is sent. |
| Client pairing security | Passed local-address, fingerprint, six-digit code, protocol identity and response validation. The Android 14 integration test exercised the Client access token through `flutter_secure_storage` with Android keystore-backed protection, verified it survived repository restart, then removed it during unpairing. Tokens, private keys and order contents were absent from logs and portable snapshots. |
| Transactional outbox | Passed atomic ticket snapshot and outbox creation for a paired Server. The durable envelope retains the stable Client installation, delivery and ticket identifiers, timestamp, heading, reference, notes, item names, quantities and checksum. A Client with no paired Server creates the same local ticket without an outbox row. |
| Independent printing | Passed code and controller checks that local printing remains gated only by the Bluetooth connection and completes its attempt before optional delivery starts. Network failure cannot roll back the saved ticket, alter printer status or create another print attempt. |
| Delivery recovery | Passed pending, sending, delivered and failed transitions, bounded foreground startup recovery, explicit retry and restart conversion of interrupted sending to pending. A simulated lost acknowledgement stored one Server order; retry reused the same identifier, received the duplicate acknowledgement and marked the original outbox row Delivered. |
| History and deletion | Passed independent delivery chips and detail status, Needs attention guidance and explicit retry. Deleting the local ticket leaves its immutable delivery record and does not change the visible order-number counter or remotely delete the Server order. |
| HTTPS receiver and receipt integrity | Passed real TLS status, one-time pairing, Bearer authentication, client-identity matching, strict JSON, request limits, transactional immutable receipt, checksum verification, duplicate acknowledgement and conflicting retry rejection. TLS 1.2 or later remains required. |
| Foreground lifecycle | Passed listener start, stop, mode switch and concurrent start/stop tests. A late TLS startup cannot survive a foreground stop. There is no background service, persistent notification, remote relay or automatic discovery. |
| Server board | Passed Received and Completed filtering, immutable order detail, source and receipt times, item quantities and notes, and persistent Mark Done. Server mode exposes no catalogue editing, printing, payment or reporting actions. |
| Mode and offline isolation | Passed confirmed Client-to-Server and Server-to-Client changes, restart persistence and preservation of both workspaces. A Client without a paired or reachable Server retains catalogue, composition, connected local printing, history, PDF sharing and portability. |
| Backup compatibility | Passed configuration and full-backup round trips, fresh-install restore, rollback and malicious archive checks for portable schema 7, with legacy schema 5 and 6 snapshots accepted. Networking tables and every pairing secret remain deliberately excluded until Task 13. |
| Accessibility and responsive localisation | Passed British English and Italian phone, landscape, tablet and doubled-text tests. All new pairing, delivery, validation, failure and retry strings are localised. |
| Representative renders | Eleven fresh previews completed without framework errors. The paired Client settings phone screen and Italian Server inbox were visually inspected: address, fingerprint, counts, controls, filters and cards are aligned and readable. Existing Overview, Compose, item, ticket and portability renders also completed. |
| Android platform integration | Passed on an unrooted Android 14 API 34 emulator. The test exercised real DataStore, SQLite schema 7, secure Server identity and Client token storage, pinned loopback pairing, authenticated delivery, listener shutdown, restart recovery and full-backup exclusion on the platform implementations. |
| Offline cold launch | Passed after a clean install of the development-signed release APK with emulator Wi-Fi and mobile data disabled. Android reported a cold launch of `io.thelicato.libreslip/.MainActivity`, the process remained alive and no fatal Android runtime entry was observed. |
| Release APK | Passed with the temporary development validation certificate. Verified version 0.12.0, application identifier `io.thelicato.libreslip`, minimum API 34, target API 36 and APK Signature Scheme v2. Flutter and Gradle APK outputs matched. |
| Permissions and backup | The release requests `BLUETOOTH_CONNECT`, `INTERNET` and Android's app-local dynamic-receiver signature permission. It requests no location or broad storage permission. `INTERNET` permits optional LAN sockets and does not make core Client operation depend on the internet. Automatic cloud backup and device transfer remain disabled. |
| Physical NETUM NT-1809DD | The user's Task 4 report confirms Bluetooth printing on the physical printer. Physical printing was not repeated for this networking milestone. Battery percentage remains unavailable because neither the printer documentation nor Android's public Classic socket API provides it. |
| Delivery artefacts | The source ZIP uses a `LibreSlip/` root and excludes caches, build state, SDK paths, signing material and previous archives. The development-signed preview APK and both-file SHA-256 list are generated by the stale-APK guarded packager. |

Task 12 implements Client pairing and delivery without automatic discovery. Physical communication between two separate Android devices on the same Wi-Fi network was not available for this milestone. The authenticated path was exercised through real loopback HTTPS in Dart and on Android 14, including secure token storage and an actual Client request reaching the foreground Server listener. Router client isolation, network changes, multiple physical clients, mDNS evaluation, networking-data backup policy and larger-queue hardening remain Task 13.

The Android document picker and share-sheet interaction were compiled into the release APK but were not manually repeated during Task 12. Export cancellation and destination behaviour remain platform-owned and unobserved here. The GitHub release workflow was not executed because no tag was pushed and no repository secrets were changed.

The physical printer result is user-reported evidence from Task 4. A transmitted printer state still means that the phone completed its socket write, not that LibreSlip can prove paper output. The app never automatically retries an uncertain print. USB printing remains outside the current implementation.

The preview APK uses a development validation certificate and is not a production upgrade baseline. The repository owner must keep the long-lived release keystore securely backed up, configure the documented GitHub secrets, and publish only from a matching `v0.12.0` tag.
