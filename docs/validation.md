# Release candidate validation

Validated on 25 September 2026 for LibreSlip 0.11.0, Android application identifier `io.thelicato.libreslip`.

| Check | Result |
| --- | --- |
| Dart formatting | Passed, 68 Dart files checked with no changes required. |
| Static analysis | Passed with no issues. |
| Unit and widget tests | All 81 active tests passed; the normal run skipped only the opt-in render capture. |
| HTTPS receiver | Passed real loopback TLS tests with a generated self-signed identity, fingerprint verification, strict JSON, one-time pairing, Bearer authentication, client-identity matching, request limits and unauthorised rejection. The listener uses TLS 1.2 or later and closes HTTP connections after each small protocol request. |
| Receipt integrity | Passed transactional immutable receipt, checksum verification, a unique client and delivery key, identical retry acknowledgement, conflicting retry rejection, line limits and persistence across repository restart. A lost acknowledgement and repeat created one Server order. |
| Foreground lifecycle | Passed start, stop, mode-switch and concurrent start/stop tests. A late TLS startup cannot survive a foreground stop. The Android integration test opened the real listener in Server mode and confirmed it closed when the Server screen was removed. No background service or persistent notification exists. |
| Secure identity and pairing | Passed stable identity reload in automated transport tests. The Android 14 integration test exercised `flutter_secure_storage` with Android keystore-backed key protection and produced a 64-character certificate fingerprint. Private keys, access tokens and order contents were absent from logs and current archive snapshots. Pairing codes remain memory-only and expire after five minutes. |
| Server board | Passed Received and Completed filtering, immutable order detail, source and receipt times, item quantities and notes, and Mark Done persistence. The board exposes no catalogue editing, printing, payment or reporting actions. Mark Done failure remains visible and leaves the order in Received. |
| Mode and Client isolation | Passed confirmed Client-to-Server and Server-to-Client changes, restart persistence and preservation of client items, drafts and ticket history. Client mode remains fully usable without a paired or reachable Server. Client delivery is not implemented in this milestone. |
| Backup compatibility | Passed existing configuration/full-backup round trips, fresh-install restore, rollback and malicious archive checks. Schema 5 snapshots remain accepted. Server inbox, paired-client metadata, private keys and access-token hashes remain deliberately excluded until Task 13. |
| Accessibility and responsive localisation | Passed British English and Italian phone, landscape, tablet and doubled-text tests. The Italian Server screen remained unclipped at doubled text size. New labels, empty states, errors, pairing and order actions are localised. |
| Representative renders | Ten fresh previews completed without framework errors. The Italian phone Server inbox with a received order was visually inspected: connection identity, pairing action, filters, order card and mode controls are aligned and readable. Existing Overview, Compose, item, history, ticket and portability renders also completed. |
| Android platform persistence | Passed on an unrooted Android 14 API 34 emulator. The integration test exercised real DataStore, SQLite, secure Server identity creation, HTTPS binding, listener shutdown, mode and installation identity persistence, draft and ticket recovery, interrupted-print recovery and independent full-backup restore. |
| Offline cold launch | Passed after a clean install of the development-signed release APK with emulator Wi-Fi and mobile data disabled. Android reported a cold launch of `io.thelicato.libreslip/.MainActivity`, the process remained alive and the activity was top-resumed with no fatal Android runtime entry. |
| Release APK | Passed with the temporary development validation certificate. Verified version 0.11.0, application identifier `io.thelicato.libreslip`, minimum API 34, target API 36 and APK Signature Scheme v2. Flutter and Gradle APK outputs matched. |
| Permissions and backup | The release requests `BLUETOOTH_CONNECT`, `INTERNET` and Android's app-local dynamic-receiver signature permission. It requests no location or broad storage permission. `INTERNET` is required for local-network sockets and does not make Client operation depend on the internet. Automatic cloud backup and device transfer remain disabled. |
| Physical NETUM NT-1809DD | The user's Task 4 report confirms Bluetooth printing on the physical printer. Physical printing was not repeated for this Server milestone. Battery percentage remains unavailable because neither the printer documentation nor Android's public Classic socket API provides it. |
| Delivery artefacts | The source ZIP uses a `LibreSlip/` root, includes the protocol specification and excludes caches, build state, SDK paths, signing material and previous archives. The development-signed preview APK and both-file SHA-256 list are generated by the stale-APK guarded packager. |

Task 11 receives authenticated orders but does not deliver them from Client mode. Task 12 must add optional pairing and delivery on the Client, transactional outbox creation with local ticket finalisation, independent delivery status and explicit interruption-safe retry. Local printing remains separate and still requires a connected printer.

The Server transport was exercised through real loopback HTTPS and through listener startup on Android 14. Physical communication between two Android devices on the same Wi-Fi network was not tested because the Client sender is not part of Task 11. Router isolation, network changes, multiple physical clients and certificate pinning in the future Client remain Task 12 or Task 13 validation work.

The Android document picker and share-sheet interaction were compiled into the release APK but were not manually exercised during Task 11. Export cancellation and destination behaviour remain platform-owned and unobserved here. The GitHub workflow was not executed because no tag was pushed and no repository secrets were changed.

The physical printer result is user-reported evidence from Task 4. A transmitted printer state still means that the phone completed its socket write, not that LibreSlip can prove paper output. The app never automatically retries an uncertain print. USB printing remains outside the current implementation.

The preview APK uses a development validation certificate and is not a production upgrade baseline. The repository owner must keep the long-lived release keystore securely backed up, configure the documented GitHub secrets, and publish only from a matching `v0.11.0` tag.
