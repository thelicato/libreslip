# Optional order management

Deliver each step as a separate, reviewable change. The existing offline composition, immutable ticket history and explicit printing workflow remains available. New order management capabilities must be optional and must work locally without a Server.

## 1. Order titles: implemented

The optional Order title / table field uses the existing persisted order reference, with an 80-character limit. Titles appear above the order number in standard and Compact Compose, ticket history and ticket details, and Server cards and details. Blank titles use the numbered view. Client Settings can hide the field; disabling it preserves the current composition content but omits it from newly saved tickets, matching the existing optional-field behaviour. Saved titles remain visible. Tickets, PDF sharing, local backups and Server delivery retain the same reference field, so existing data and paired devices remain compatible. No database, archive or protocol migration is required.

## 2. Course groups: implemented

Client Settings enables named, ordered courses, for example Drinks, First course and Second course. The option is off by default. Standard and Compact Compose, Server cards and details, previews, 58 mm preparation tickets and PDFs visually separate courses. Select a course for additions or move individual lines; the same item in different courses keeps separate quantities and notes. Manage courses to rename, reorder or remove them, with removal returning items to Ungrouped. Empty courses are omitted from rendered tickets. When enabled, the next composition reuses course definitions; disabling preserves the current order and saved snapshots and returns the next composition to the ordinary layout.

Transactional SQLite schema 11 stores course definitions, line references, active selection and the optional setting. Configuration document version 2 and full backups round-trip the new data, accept older formats and validate course relationships before restore. Plain delivery retains envelope version 1; grouped delivery uses version 2 and checks the pinned Server's advertised support before posting. Unsupported deliveries remain available for explicit retry after updating the Server. Course groups provide visual organisation; they do not yet schedule preparation, update saved orders or track delivery progress.

## 3. Updates to active orders: implemented

The disabled-by-default Keep orders open option retains new submitted orders in a separate active-order store. Compose can select an active order when the single composition is empty, add catalogue items and print a labelled additions ticket. Existing lines, title, order notes, heading and previously used courses stay fixed; new courses can be appended. Adding the same product creates a separate stable line with its own quantity and preparation note. Each submission saves the complete order as an immutable revision, while print, reprint and PDF output contain only that revision's additions. Ticket details can expand the full snapshot. Closing an active order stops further additions without deleting its tickets or changing Server completion. Disabling the option affects new orders and retains existing active orders.

Transactional SQLite schema 12 stores active orders independently of the editor and history, links additions to an expected base revision and prevents duplicate finalisation. Configuration document version 3 and full backups preserve the option, current orders, revision snapshots and interrupted additions. Plain and grouped ordinary tickets keep envelope versions 1 and 2. Managed delivery uses version 3, stable order and line identifiers and consecutive revisions; unsupported Servers receive no order POST. By default, every Server-bound revision waits for its own successful byte transmission and acknowledgement of earlier revisions. Step 6 lets newly created deliveries proceed without printing while retaining acknowledgement ordering. Explicit recovery retains the same envelope and print bytes. The Server updates one order, rejects stale or conflicting changes, highlights additions and returns a completed order to Received while excluding previously completed lines from preparation totals.

An active order retains its original Server destination and per-line Local only choices. Orders started unpaired remain local. Moving a backup to a different installation restores active orders for local additions without recreating networking credentials or deliveries. Restore on the original installation does not rewind a Server; a stale revision is rejected. Managed tickets with unfinished Server delivery cannot be deleted because they are needed for print recovery and revision ordering. Client item statistics count additions rather than counting the same items again in every full snapshot. This step supports additions; edits or removal of already submitted items and per-item delivery remain outside its scope.

## 4a. Per-item delivery on each device: implemented

Keep orders open also enables delivery tracking for retained active orders. In Active orders, expand Delivery progress to mark individual units, mark a whole line delivered or undo a delivery. Previously ordered content stays fixed. Outstanding and fully delivered lines are visually separated within each course, with partial counts on each line. New additions start outstanding even when the same product was delivered earlier. Delivery edits need no printer, Server or internet and do not create tickets, print jobs or transactions. Fully delivered Client orders stay open for additions until explicitly closed. Disabling Keep orders open retains controls for existing active orders.

Managed Server orders use the same controls in their details. Preparation totals subtract delivered quantities. Delivering every item moves the order to Completed; undoing any unit returns it to Received. Done marks all items delivered and Undo Done resets every delivered quantity. Additions return the order to Received and preserve prior line progress. Ordinary tickets retain their existing Received/Done workflow and do not expose per-item controls. Transactional SQLite schema 13 preserves earlier Server completion markers as delivered quantities during migration and stores Client progress independently of saved content. Full backups retain and validate Client progress; schema 12 backups restore with zero Client deliveries. Server inbox data remains outside backups.

Step 4a introduced independent tracking. Step 4b adds explicit exchange while retaining offline controls.

## 4b. Paired delivery progress synchronisation: implemented

In Active orders, expand Delivery progress and select Sync progress to exchange counts with the original paired Server. There is no automatic polling or progress retry. Delivery and undo remain available offline, without a printer, and never rewrite saved tickets. Server completion and undo follow the resulting quantities; fully delivered Client orders stay open. Local only counts remain private. Shared additions must reach the Server before progress can be exchanged. An older Server receives no progress requests until upgraded; an order restored to a different installation continues locally.

SQLite schema 14 records local edit identities, including zero-valued undo, monotonic progress revisions, an immutable pending operation and Server idempotency receipts. A lost acknowledgement retries the same operation on the next explicit action, then reads current Server progress so later Server edits are retained. Concurrent differences require a visible choice of all shared Client or Server counts; cancellation preserves offline work. A choice made against an obsolete Server revision is rejected and refreshed. Full backups retain local edit intent but exclude pending operations, baselines, receipts and credentials. Failed or interrupted restore preserves pending operations in an app-private rollback journal. Legacy schema 13 data conservatively marks every line edited to protect unknown undo history.

## 5. Optional product prices and totals: implemented

The October 2026 request explicitly revises the earlier prohibition on prices and monetary totals for this optional feature. Product prices and estimates is disabled by default and independent of managed orders and courses. The item editor accepts an optional unit price with an explicit EUR, GBP or USD currency. Values use integer minor units from zero through 99,999,999, with at most two fractional digits. Empty values mean no price; zero is distinct. Estimates group integer subtotals by currency without conversion, flag unpriced quantities and include delivered items. Compose, Active orders and ticket details show estimates only when enabled. An expandable breakdown shows unit prices and line estimates.

Prices are captured when a catalogue item is first added to the composition and persist across restart. Increasing an existing line keeps its captured price. Remove and re-add an editable line to adopt a changed catalogue price. Immutable tickets and current managed orders retain snapshots, while additions capture their own prices. Disabling the option hides prices, preserves existing catalogue and snapshot data, and omits prices from newly saved tickets and additions. Preparation printing, previews, ticket PDFs and Server envelopes retain their existing content; estimates remain local.

Transactional SQLite schema 15 adds bounded nullable price and currency pairs to catalogue, composition and ticket lines, explicit prices in managed line inventories, and the optional setting. Existing data migrates with absent prices and the option disabled. Configuration document version 4 and full backups preserve and validate the option and snapshots; legacy formats remain accepted with disabled defaults. Validation rejects unsupported currencies, mismatched pairs, fractional or excessive minor units, missing modern fields and inconsistent prices between current orders and saved revisions. Restore rollback also preserves priced snapshots. Payment processing, payment recording, checkout, taxes, discounts, refunds and financial reporting remain outside scope.

## 6. Optional printer connection: implemented

Client Settings adds Require printer connection, on by default. Switching it off enables Save order and Save additions without a connected printer, saving the same immutable snapshots without creating print attempts. Eligible Server envelopes are ready immediately. Connected printing and explicit reprints retain their normal connection guards. The policy is captured for each new outbox row; changing the preference cannot release older Waiting for print entries or bypass earlier managed revisions. Settings format 8 persists and backs up the preference, while versions 1 through 7 migrate with it enabled. Database schema 15 and network protocol formats remain unchanged.

## 7. Unnamed order dividers: implemented

Order dividers replaces the named course composer with Add divider. Add items, insert a boundary and add the next items below it. No name entry or group-management dialog is needed. Standard and Compact Compose share teal rules with a small central detail; Client delivery progress, Server cards and details, history, ticket previews, printing and PDFs retain the same split. Item arrows move editable lines across boundaries, and Remove last divider joins the last two sections without changing quantities, notes or identifiers. Empty repeated boundaries are prevented. Existing committed managed boundaries remain fixed and new orders start with no inherited divisions.

The disabled-by-default setting retains the existing `courseGroupsEnabled` preference. Stable divider identifiers and automatic ordinal tokens reuse the bounded group snapshots, so database, archive and protocol formats remain unchanged. Existing saved named content stays immutable and retains its captions. Older grouped-order Servers preserve sections but display the token; updated Servers show an unlabelled rule.

## Validation and delivery

Each step includes formatting, analysis, relevant automated checks, localised responsive render inspection, source ZIP and a development-key Android preview when buildable. Changes to persistence, protocols or restore require migration, interruption and invalid-restore tests. Automated byte transmission and rendered previews do not establish physical printer output; Android and physical hardware checks must be reported separately.

## 8. Shared managed orders: implemented

With Keep orders open enabled, foreground Clients paired with the same updated Server receive its managed orders and can add catalogue items or change delivered quantities. Refresh runs every five seconds and after local changes; revision headers avoid fetching unchanged snapshots. Received mirrors contain preparation content and current progress without importing catalogue rows, private prices, ticket history or print jobs. Local only lines remain private.

Concurrent additions append stable identifiers transactionally, retain other Clients' changes and preserve original Server identity. Unnamed divider markers stay unique. Delivery edits on different lines merge; same-line conflicts retain local intent across repeated polling and expose explicit Client or Server choices. Lost acknowledgements retry the original durable identity. Existing printer readiness still gates additions, and offline composition and recovery remain available. Current additions rebase against incoming content without changing their selected lines. Closing an order hides it only on that Client, and deleting it on the Server marks cached views unavailable without deleting local work.

Schema 16 adds private link and append-receipt tables. Version 1 shared capability negotiation uses separate authenticated pinned HTTPS routes; earlier envelope and explicit progress formats remain intact. Configuration and full backups exclude network metadata, while private failed or interrupted restore recovery retains exact pending operations. Automatic sharing pauses when Keep orders open is disabled, in Server mode and when the Client app leaves the foreground.

## 9. Multiple simultaneous Server connections: implemented

Client Settings retains every paired Server and exposes independent disconnect and queue counts. The latest pairing is selected for new orders, and Use for new orders or the Compose destination selector changes that choice. Each new ticket uses one selected destination; existing order additions and progress keep their original route. Active orders identify their Server when several are connected. Delivery drains and shared feeds run independently for each Server, with preparation merges serialised under the composition writer lock. A slow or unreachable Server leaves the others usable.

Schema 17 migrates the previous active destination to the selected destination and replaces the single-active index with a unique selection index. Selection survives restart and remains installation-local. Unpairing removes only that Server’s credential, retains queued work and selects a remaining Server. Full backups exclude connections and secrets; existing offline, single-Server and printer readiness workflows retain their behaviour. There is no new network protocol or Server upgrade requirement for multiple destinations.
